### 1. LLM은 Google Gemini API 무료 사용량으로 시작

- 날짜: 2026-11-16
- 출처: 사용자 결정 (커리큘럼 과제 2)
- 결정: 과제 2부터 Gemini API의 무료 사용량을 쓴다.
- 이유
  - 비용 없이, 실무처럼 API로 모델을 호출하고 로그·비용을 관리하는 연습을 그대로 할 수 있다.
  - 실제 요금이 0원이므로 비용 한도는 "1토큰당 단가"를 직접 정해 두고 계산해서 시험한다.
- 고르지 않은 선택지
  - 구독으로 Claude Code 호출(`claude -p`): 모델 위에 Claude Code가 한 겹 씌워져 지시를 어긴 원인을 가르기 어렵고, 13주차에 다른 사용자에게 열 수 없다.
  - 로컬 Ollama: 모델 직접 서빙은 과제 10에서 배우고, 작은 모델로는 통과 기준을 넘기 어려울 수 있다.
  - 유료 API 소액 충전: 돈을 쓰지 않기로 했다. 과제 6(비용 줄이기)에서 프롬프트 캐싱 할인 등을 겪으려면 다시 정한다.
- 주의할 점
  - 무료로 보낸 데이터는 모델 개선에 쓰일 수 있다. 개인정보·회사 자료를 넣지 않는다. 시작할 때 약관을 확인한다.
  - OpenAI 호환 엔드포인트가 있는지 공식 문서에서 확인하고, 있으면 그걸 쓴다. 나중에 제공사를 바꿀 때 URL과 키만 바꾸면 되게 하기 위해서다.
- 상태: 예정 (과제 2에서 적용)

### 2. 배포 대상은 AWS Lambda (컨테이너 이미지 + Lambda Web Adapter)

- 날짜: 2026-11-19
- 출처: 사용자 결정 (커리큘럼 과제 1)
- 결정: 도커 이미지를 ECR에 올리고, Lambda Web Adapter로 FastAPI를 코드 수정 없이 Lambda에서 띄운다. 주소는 함수 URL로 연다.
- 이유
  - 요청이 없으면 비용이 0이고, 혼자 쓰는 규모는 무료 사용량 안에 든다.
  - ECR·IAM·CloudWatch를 그대로 익힌다.
  - 같은 도커 이미지를 과제 9에서 Kubernetes로 옮길 수 있다.
- 고르지 않은 선택지
  - ECS·Fargate: 켜 두는 동안 계속 비용이 든다.
  - EC2: 무료 기간이 끝나면 비용이 들고 서버를 직접 관리해야 한다.
  - Google Cloud Run: 더 단순하지만 AWS 경험이 필요하다(공고 요구).
- 주의할 점: Lambda를 VPC에 넣지 않으므로 VPC 경험이 빠진다. VPC 안에 Lambda와 RDS를 붙이는 실습을 몇 시간만 따로 하고 바로 지운다. 그 전에 예산 알림을 건다.
- 상태: 진행 중 (Dockerfile, ECR·IAM·로그 그룹 Terraform 작성됨)

### 3. 인프라는 Terraform, 도커 빌드·push는 터미널 명령

- 날짜: 2026-11-19
- 출처: 사용자 결정 (커리큘럼 과제 1)
- 결정: ECR·IAM 역할·로그 그룹·Lambda 함수·함수 URL을 Terraform으로 만든다. 도커 빌드와 push는 Terraform 밖에서 터미널 명령으로 한다.
- 이유: 과제 9에서 EKS를 Terraform으로 만들기 전에, 작은 구성으로 먼저 익힌다.
- 고르지 않은 선택지
  - AWS SAM·CDK: Lambda에는 더 편하지만 AWS에서만 쓰인다.
  - Terraform으로 도커 빌드까지 하기: 실패했을 때 Terraform 문제인지 도커 문제인지 가르기 어렵다.
- 지킬 것
  - `terraform.tfstate`는 git에 올리지 않는다(AWS 자원 정보가 그대로 들어 있다).
  - 비밀값은 `.tf`에 쓰지 않고 SSM Parameter Store에 둔다.
  - 이미지 태그 규칙은 5번 참고.
- 상태: 진행 중
- 변경됨: 2026-11-21, "도커 빌드·push는 터미널 명령" 부분은 8번(GitHub Actions)으로 대체. Terraform으로 인프라를 만드는 부분은 그대로.

### 4. DB는 Supabase Postgres 무료 요금제 + pgvector

- 날짜: 2026-11-19
- 출처: 사용자 결정 (커리큘럼 과제 2)
- 결정: Supabase의 Postgres 무료 요금제를 쓰고, 과제 3의 벡터도 pgvector로 같은 DB에 둔다.
- 이유
  - 비용이 들지 않는다.
  - SQL과 벡터 검색을 DB 하나로 처리한다. Postgres와 pgvector는 실무에서도 그대로 쓴다.
  - Lambda를 VPC에 넣지 않아도 접속할 수 있어 NAT 게이트웨이 비용이 없다.
- 접속 방법
  - Lambda 컨테이너가 늘면 DB 연결 수가 넘칠 수 있으므로 Supabase 풀러 주소(포트 6543)로 붙는다.
  - DB 비밀번호는 SSM Parameter Store(기본 등급 무료)에 둔다.
- 고르지 않은 선택지
  - AWS RDS·Aurora: 무료 기간 뒤 매달 비용이 들고, VPC 안에 있어 Lambda가 Gemini를 부르려면 NAT 게이트웨이 비용이 든다.
  - DynamoDB: SQL을 쓸 수 없고 벡터를 따로 둬야 한다.
  - Neon: 비슷한 무료 Postgres. 일시 정지 문제가 없어 대안으로 남겨 둔다.
- 주의할 점: 무료 요금제 제한(용량 약 500MB, 일주일 동안 요청이 없으면 일시 정지)은 확인하지 않은 값이다. 시작할 때 확인한다.
- 상태: 예정 (과제 2에서 적용)

### 5. 이미지 태그는 Git 커밋 번호로 자동 지정

- 날짜: 2026-11-19 (커리큘럼 과제 1에서 정함), 2026-11-21 (CI 자동화 방법 추가)
- 출처: 사용자 결정 + 사용자 질문 — "커밋 번호로 태그를 달면 매번 손으로 적어야 하지 않나?"
- 결정
  - 이미지 태그는 `latest` 대신 git 커밋 번호로 한다.
  - CI를 붙인 뒤에는 `${{ github.sha }}`(이번 실행을 일으킨 커밋 번호)를 태그로 써서 사람이 적지 않게 한다.
- 이유
  - 태그가 매번 같으면 Terraform이 이미지가 바뀐 것을 알아채지 못한다.
  - 이미지가 정확히 어느 코드로 만들어졌는지 바로 알 수 있다.
  - 문제가 생기면 이전 커밋 번호의 이미지로 되돌릴 수 있다.
- 고르지 않은 선택지
  - `latest` 태그 함께 쓰기: ECR 저장소가 `IMMUTABLE`(한 번 붙인 태그를 다른 이미지로 옮길 수 없음)이라 두 번째 push부터 실패한다.
  - 버전 번호(`v1.2.0`): 사람이 정해 붙여야 해서 수작업 문제가 다시 생긴다.
  - 날짜·시간 태그: 자동이지만 어느 코드로 만든 이미지인지 알 수 없다.
- 주의할 점: 커밋마다 이미지가 쌓이므로 ECR 수명 주기 정책(예: 최근 N개만 보관)이 필요하다.
- 상태: 커밋 번호 태그와 CI 자동화 모두 과제 1에서 진행 (8번 참고)

### 6. API 코드와 LLM 설정을 분리 — 설정만 바뀌면 이미지를 다시 만들지 않는다

- 날짜: 2026-11-21
- 출처: 사용자 제안
- 결정
  - API 코드(`src/`, `Dockerfile`, `pyproject.toml`, `uv.lock`)가 바뀌면 이미지를 새로 빌드해 ECR에 push 한다.
  - LLM 설정(모델 이름, temperature, 최대 토큰 수, 시스템 프롬프트 등)은 이미지 밖에 두고, 값만 바뀌면 이미지는 그대로 둔다.
- 이유
  - 설정값 하나 고칠 때마다 빌드·push 하는 시간과 ECR 저장 비용이 들지 않는다.
  - `config.py`가 이미 `pydantic-settings`로 환경 변수를 읽으므로 구조상 바로 가능하다.
- 설정을 두는 곳(후보)
  - Lambda 환경 변수: 값이 적을 때 가장 단순하다.
  - SSM Parameter Store / Secrets Manager: API 키처럼 숨겨야 하는 값.
  - S3 설정 파일: 시스템 프롬프트처럼 긴 값.
- 반영 방법: Lambda 환경 변수를 바꾸면(`update-function-configuration`) 이후 호출부터 새 값이 쓰인다. 이미지 재배포는 필요 없다.
- 주의할 점
  - 이미 있는 설정 항목의 **값**만 바꿀 때만 이미지 없이 된다. 새 항목을 추가하면 그걸 읽는 코드가 필요하므로 이미지도 새로 만들어야 한다.
  - 콘솔에서 손으로 바꾸면 이전 값이 남지 않는다. 설정도 Git에 두고 CI로 올려야 되돌릴 수 있다.
  - 응답 로그에 "지금 쓰는 설정 버전"을 남겨야 답변 품질이 바뀌었을 때 원인을 찾을 수 있다.
- 상태: 예정 (설정 저장 위치 미정)

### 7. CI/CD 도구는 GitHub Actions

- 날짜: 2026-11-21
- 출처: 사용자 질문 — "취업이 목적이면 CI/CD 도구는 무엇으로?" (커리큘럼 과제 7에도 GitHub Actions로 적혀 있음)
- 결정: GitHub Actions를 쓴다.
- 이유
  - 워크플로 파일과 실행 기록이 저장소에 남아 포트폴리오로 바로 보여 줄 수 있다.
  - 별도 서버를 설치·관리할 필요가 없다. 공개 저장소는 무료다.
  - AWS가 공식 액션(`aws-actions/configure-aws-credentials`, `amazon-ecr-login`)을 제공해 ECR 연동이 쉽다.
- 고르지 않은 선택지
  - Jenkins: 국내 기존 회사에서 많이 쓰이지만 서버를 직접 운영해야 해 혼자 공부하기엔 부담이 크다. 개념만 알아 둔다.
  - GitLab CI: 방식이 거의 같아 GitHub Actions를 알면 쉽게 옮길 수 있다.
  - AWS CodePipeline / CodeBuild: 설정이 AWS 콘솔에 흩어져 보여 주기 어렵다.
  - Argo CD: 쿠버네티스용 배포 도구라 지금 단계엔 이르다(과제 9에서 다룬다).
- 주의할 점
  - 처음엔 AWS 키를 GitHub Secrets에 넣어 동작을 확인하고, 이후 OIDC(키를 저장하지 않고 실행 때마다 임시 권한을 받는 방식)로 바꾼다.
  - 공개 저장소이므로 비밀값은 반드시 Secrets에만 둔다.
- 상태: 진행 중 (과제 1로 앞당김, 8번 참고)

### 8. CI/CD를 과제 7에서 과제 1로 앞당김

- 날짜: 2026-11-21
- 출처: 사용자 결정
- 결정: 이미지 빌드와 ECR push를 터미널 명령 대신 GitHub Actions로 자동화하는 작업을 지금(과제 1) 한다. 커리큘럼에서는 과제 7에 배우기로 했던 내용이다.
- 이유
  - 과제 1을 하다가 실제 문제를 겪었다. 이미지 태그를 git 커밋 번호로 달기로 했는데(5번), 터미널로 하면 커밋할 때마다 번호를 손으로 적어야 한다.
  - 겪은 문제를 넘기지 않고 자동화로 해결한 과정 자체가 포트폴리오에서 더 좋은 근거가 된다.
- 고르지 않은 선택지
  - 커리큘럼 순서대로 과제 7까지 미루기: 과제 1 동안 수작업 태그를 계속 감수해야 하고, 문제를 겪은 시점과 해결한 시점이 멀어진다.
  - 터미널용 스크립트로 커밋 번호를 자동으로 넣기: 수작업은 줄지만 push 할 때 자동으로 돌지 않고, 저장소에 실행 기록이 남지 않는다.
- 주의할 점
  - 3번에서 터미널 명령을 고른 이유는 "실패했을 때 Terraform 문제인지 도커 문제인지 가르기 쉽게"였다. CI를 붙이면 의심할 곳이 하나 더 늘어난다. 터미널로 한 번 빌드·push 해서 이미지가 Lambda에서 도는 것을 먼저 확인하고 CI를 붙이면 원인을 가르기 쉽다.
  - 과제 7에서 배울 배포 게이트(점수가 떨어지면 배포 막기)와 롤백은 이번 범위가 아니다. 이번에는 "빌드와 push 자동화"까지만 한다.
- 상태: 진행 중
- 변경됨: 2026-11-21, 범위에 자동 검사(pytest)를 더함. 9번 참고.

### 9. CI에 자동 검사(pytest)도 지금 넣는다 — 검사를 통과해야 이미지를 올린다

- 날짜: 2026-11-21
- 출처: 사용자 제안 — "지금 test도 있으니까 test도 넣어서"
- 결정: CI에서 pytest를 먼저 돌리고, 통과했을 때만 이미지를 빌드·push 한다. 커리큘럼에서는 과제 7의 첫 단계(자동 검사)였던 내용이다.
- 이유
  - 과제 1에서 이미 테스트(`test_main.py`)를 만들었다. 있는 테스트를 돌리지 않고 이미지를 올리면, 깨진 코드의 이미지가 ECR에 올라갈 수 있다.
  - 빌드·push를 자동화하는 김에 검사도 같은 흐름에 넣으면, "검사 → 빌드 → push" 순서가 처음부터 잡힌다.
- 고르지 않은 선택지
  - 과제 7까지 미루기: 테스트가 이미 있는데 자동으로 안 돌리면, 손으로 돌리는 것을 잊은 날 깨진 이미지가 올라간다.
- 주의할 점
  - `test_health`는 `OK_MESSAGE` 설정값을 읽는다. 이 값은 `.env`에 있는데 `.env`는 git에 올리지 않으므로, CI에서는 따로 넣어 주지 않으면 테스트가 실패한다.
  - 검사와 빌드를 한 워크플로 파일에 둘지 나눌지는 아직 정하지 않았다. "검사 통과 후에만 올린다"는 순서를 걸기에는 한 파일 안에서 job 순서(`needs`)를 쓰는 쪽이 단순하다.
  - 배포 게이트(점수 기준)와 롤백은 여전히 과제 7에서 한다.
- 상태: 진행 중

### 10. CI의 AWS 접속 키는 작업용 IAM 사용자의 키를 쓴다

- 날짜: 2026-11-21
- 출처: 사용자 결정
- 결정: GitHub Secrets(`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`)에 과제 1에서 만든 작업용 IAM 사용자의 액세스 키를 넣는다.
- 이유: 가장 빨리 CI를 돌려 볼 수 있다. 새 사용자와 권한을 따로 설계하지 않아도 된다.
- 고르지 않은 선택지
  - CI 전용 IAM 사용자(ECR push 권한만): 키가 새어도 피해가 이미지 올리기로 한정되지만, 지금은 설정을 늘리지 않기로 했다.
  - OIDC(키를 저장하지 않고 실행마다 임시 권한을 받기): 가장 안전하지만 설정이 더 복잡하다. 7번에 적은 대로 키 방식으로 먼저 확인한 뒤 바꾼다.
